# Modified-XRAY — транспорт **packet-down** для XHTTP

Учебный / исследовательский проект (НИР). Модификация транспортного слоя
[Xray-core](https://github.com/XTLS/Xray-core): новый режим работы XHTTP под
названием **packet-down**, задача которого — сделать нисходящий (download)
трафик туннеля менее отличимым от обычного веб-сёрфинга для систем глубокого
анализа трафика (DPI).

> ⚠️ Проект создан в учебно-исследовательских целях для изучения методов
> анализа и маскировки трафика. Не предназначен для распространения.

## 2. Зачем это нужно: проблема

Чтобы обойти блокировки, трафик прокси маскируют под обычный HTTPS. Стек
выглядит так:

```
Приложение → VLESS → XHTTP → REALITY (вместо TLS) → TCP
```

- **VLESS** — прикладной слой: кто вы и куда проксировать. Сам не маскирует.
- **REALITY** — замена TLS: делает рукопожатие неотличимым от подключения к
  настоящему чужому сайту («донор»). Защищает на этапе рукопожатия и от
  активного зондирования.
- **XHTTP** — транспорт: упаковывает поток прокси в обычные HTTP-запросы.

REALITY хорошо защищает **рукопожатие**. Но борьба с цензурой сместилась на
**поведение трафика после рукопожатия**, и здесь у стандартного XHTTP есть
заметная структурная слабость.

### Слабость стандартного XHTTP (режим packet-up)

В режиме `packet-up` трафик выглядит так:

```
Upload (вверх):   POST /path/<uuid>/0 , /1 , /2 …   (много коротких запросов)
Download (вниз):  GET  /path/<uuid>                 (ОДИН бесконечный ответ)
```

Картина «**один очень долгий GET + множество коротких POST на один и тот же
путь**» нехарактерна для обычного веба. Это поведенческий признак, по которому
DPI могут выделить туннель. В исходных материалах по XHTTP эта
слабость отмечается прямо: длинный одиночный GET — узкое место маскировки.

---

## 3. Идея проекта: режим packet-down

**packet-down** заменяет один бесконечный GET на **серию коротких GET-запросов**
с ограниченным размером ответа — по аналогии с тем, как браузер загружает
сегменты видео (HLS/DASH) или части страницы:

```
Upload (вверх):   POST /path/<uuid>/0 , /1 , /2 …     (без изменений)
Download (вниз):  GET  /path/<uuid>/d0  → ответ ≤ N байт, конец
                  GET  /path/<uuid>/d1  → следующий «сегмент», конец
                  GET  /path/<uuid>/d2  → …
```

**Зачем именно так:** серия обычных GET с ответами конечной длины гораздо больше
похожа на нормальную веб-загрузку, чем один бесконечный GET. Признак «долгий GET
+ куча POST» исчезает — а значит, исчезает один из поведенческих маркеров
туннеля.

**Проблема решения:** последовательные запросы добавляют задержку, поэтому download
в packet-down медленнее, чем бесконечный поток. Это осознанный компромисс
«скорость против незаметности».

### Как это отличать на сервере

Номер download-сегмента помечается префиксом **`d`** (`d0`, `d1`, …).
Upload-пакеты остаются чисто числовыми (`0`, `1`, …). Так сервер однозначно
отличает «запрос сегмента вниз» от «данных вверх», не меняя структуру путей.
Это важно, потому что в XHTTP GET с номером по умолчанию уже может означать
upload (параметр `uplinkHTTPMethod`), и без префикса возник бы конфликт.

### Механика

- **Сервер** на каждую сессию заводит исходящий буфер (`downlinkBuffer`). Ядро
  Xray пишет туда данные, а каждый `GET d<N>` забирает из буфера порцию: до `N`
  байт, либо то, что накопилось за короткий интервал (long-poll), и закрывает
  ответ. Когда соединение завершено — отдаёт пустой ответ с заголовком-маркером
  `X-Pd-Eof`.
- **Клиент** вместо одного бесконечного GET запускает цикл: запрашивает `d0`,
  `d1`, `d2`… и склеивает сегменты в непрерывный поток для ядра Xray. Получив
  `X-Pd-Eof`, закрывает поток.

---

## 4. Что это НЕ решает

- **Upload остаётся прежним.** packet-down улучшает только download. Восходящий
  канал — это по-прежнему последовательные POST, а значит, остаётся два признака:
  необычное соотношение upload/download (у туннеля ≈1:2–1:3 против ≈1:10–1:50 у
  веба) и регулярность POST-запросов. То есть доработка **смещает слабое место с
  download на upload** — это честный результат и направление для дальнейшей работы.
- **Совместимость.** Режим понимают только клиент и сервер на **этой** сборке.
  Стандартные клиенты (v2rayN, v2rayNG и т. п.) про `packet-down` не знают.

## 6. Что именно изменено в коде

Вся доработка — в транспорте XHTTP (`transport/internet/splithttp/`) и парсере
конфига:

| Файл | Что сделано | Зачем |
|---|---|---|
| `transport/internet/splithttp/packet_down.go` | **Новый файл.** Исходящий буфер сессии `downlinkBuffer` (Write / TakeSegment / Close) с обратным давлением и long-poll. | Посредник между ядром Xray и короткими GET-сегментами: ядро пишет поток, сегменты забирают порции. |
| `transport/internet/splithttp/hub.go` | Поле `downlink` в сессии; распознавание `GET d<N>`; метод `serveDownlinkSegment` (создание соединения на первом сегменте, отдача порций, `X-Pd-Eof`). | Серверная половина режима. |
| `transport/internet/splithttp/client.go` | Метод `GetSegment` (один конечный GET за сегментом, чтение `X-Pd-Eof`); режим добавлен в интерфейс `DialerClient`. | Клиентский запрос одного сегмента. |
| `transport/internet/splithttp/dialer.go` | Ветка `mode == "packet-down"`: цикл запросов `d0, d1…` и запись в поток ядра. | Клиентская половина: сборка сегментов в поток. |
| `transport/internet/splithttp/browser_client.go` | Заглушка `GetSegment` (режим в браузерном диалере не поддержан). | Чтобы собиралась реализация интерфейса. |
| `infra/conf/transport_method.go` | В список режимов добавлен `"packet-down"`. | Иначе парсер отвергает конфиг. |
| `core/core.go` | Метка сборки / дисклеймер НИР. | Чтобы в `xray version` было видно, что это учебная сборка. |

## 7. Сборка

Нужен Go той версии, что указана в `go.mod` (проект собран на go1.27.3).
Метка `PET-MEPHI-PROJECT` помечает учебную сборку в выводе `xray version`.

**Linux:**
```bash
CGO_ENABLED=0 go build -o xray -trimpath -buildvcs=false \
  -ldflags "-s -w -buildid= -X github.com/xtls/xray-core/core.build=PET-MEPHI-PROJECT" ./main
./xray version      # в строке версии должно быть PET-MEPHI-PROJECT
```

**Windows (кросс-сборка):**
```bash
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -o xray.exe -trimpath -buildvcs=false \
  -ldflags "-s -w -buildid= -X github.com/xtls/xray-core/core.build=PET-MEPHI-PROJECT" ./main
```

> И клиент, и сервер должны работать на **одной и той же** сборке — иначе
> возможны ошибки из-за несовпадения версий протокола.

## 8. Установка на сервер

1. Арендовать VPS (Linux, Ubuntu 22.04/24.04, KVM, выделенный IPv4).
2. Поставить официальный Xray (для systemd-сервиса и структуры папок):
   ```bash
   bash -c "$(curl -L https://github.com/XTLS/Xray-install/raw/main/install-release.sh)" @ install
   ```
3. Заменить бинарник на **свою** сборку:
   ```bash
   systemctl stop xray
   install -m 755 ./xray /usr/local/bin/xray
   xray version        # убедиться, что метка PET-MEPHI-PROJECT
   ```
4. Сгенерировать секреты:
   ```bash
   xray uuid            # UUID клиента
   xray x25519          # пара ключей REALITY (приватный — на сервер, публичный — клиенту)
   openssl rand -hex 8  # shortId
   ```
5. Выбрать донора REALITY (крупный сайт с TLS 1.3, НЕ за CDN; желательно в той
   же стране/подсети, что и VPS):
   ```bash
   xray tls ping ВАШ-ДОНОР       # нужен TLS 1.3 и IP не из диапазонов CDN
   ```
6. Положить конфиг `config.json` (см. `config.server.example.json`), подставив
   свои значения, и запустить:
   ```bash
   xray run -test -c /usr/local/etc/xray/config.json   # Configuration OK
   systemctl restart xray
   journalctl -u xray -n 20
   ```

Файрвол: открыть порты `443` (эталонный Vision+REALITY) и `8443` (XHTTP).

## 9. Запуск клиента

1. Положить рядом свою сборку `xray`/`xray.exe`, файлы `geoip.dat`, `geosite.dat`
   и `client.json` (см. `client.example.json`).
2. Запуск:
   ```bash
   ./xray run -c client.json
   ```
3. Клиент поднимает локальный SOCKS-прокси (порт `10809` — packet-down).
   Направить в него браузер (SOCKS5 `127.0.0.1:10809`) или проверить:
   ```bash
   curl -x socks5h://127.0.0.1:10809 https://ifconfig.me
   # должен вернуть IP сервера
   ```

Проверка многосегментной передачи:
```bash
curl -x socks5h://127.0.0.1:10809 -o /dev/null -w "%{http_code} %{size_download}\n" \
  "https://speed.cloudflare.com/__down?bytes=1048576"
# ожидается: 200 1048576
```
